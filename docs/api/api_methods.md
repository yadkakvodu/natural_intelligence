### 1. Общее описание
Метод предназначен для формирования ленты персональных бизнес-инсайтов для конкретного клиента крупного бизнеса. Система автоматически отбирает значимые события из внешних новостей и аналитики Альфа-Банка, сопоставляет их с профилем компании (ОКВЭД, продукты банка, ВЭД, выручка) и возвращает список с оценкой релевантности и тегами влияния.

**Пример экрана:** Левая колонка интерфейса «Новостной консультант». Карточки новостей содержат заголовок, дату, источник, процент релевантности и цветовой тег категории («критично», «регуляторное», «возможность»).

### 3. Связанные документы
*   **БД:** `public.clients`, `public.news` (см. DDL скрипт проекта)
*   **Figma:** Макет «Новостной консультант» (левая панель)
*   **Кейс:** Альфа Хак_Новостная аналитика.pdf (стр. 6-7, 14)
*   **Архитектура:** Схема взаимодействия Java API и Python Agent Core

### 4. Доступы и ограничения
*   **Доступен без авторизации (для целей демо).** Идентификация клиента осуществляется через path-параметр `synthetic_u`.
    *   *Примечание:* В боевой системе требуется Bearer Token и проверка прав доступа. Для хакатона используется упрощенная схема.
*   **Rate Limit:** Не более 30 запросов в минуту (глобальный лимит для защиты бюджета LLM в 500р). При превышении возвращается HTTP-429.
*   **Идемпотентность:** Метод идемпотентен. Повторный запрос с теми же параметрами возвращает тот же результат (если не появились новые данные в БД).

### 5. Пример запроса
**Тип метода:** GET  
**URL:** `https://alfa-hack-demo.ru/api/clients/U_80/news-feed`

**Headers:**
```http
Accept: application/json
```

**Query Parameters:**
| Параметр | Тип | Обяз. | Описание |
| :--- | :--- | :--- | :--- |
| limit | int | Нет | Количество инсайтов в ответе. По умолчанию 5, макс 20. |
| offset | int | Нет | Смещение для пагинации. По умолчанию 0. |
| order | string | Нет | Сортировка. Формат: `order=published_at,desc`. По умолчанию по релевантности. |
| is_analytics_only | boolean | Нет | Фильтр: показывать только аналитику Альфа-Банка. |
| topic | string | Нет | Фильтр по теме новости (например, 'cbr_rate', 'ved'). |

### 8. Требования к реализации (Алгоритм работы)
1.  **Валидация входных данных:**
    *   Проверить формат `synthetic_u` (должен начинаться с 'U_'). Если нет → HTTP-400.
    *   Проверить `limit` (1-20), `offset` (>=0).
    *   Проверить формат `order`.
2.  **Проверка Rate Limit:**
    *   Проверить глобальный счетчик запросов за последние 60 сек. Если >30 → HTTP-429.
3.  **Получение профиля клиента:**
    *   Выполнить запрос к `clients` по `synthetic_u`.
    *   Если запись не найдена → HTTP-404.
    *   Извлечь семантические признаки: `mainokved_code`, `cl_product_loa_mark`, `fts_flag`, `fts_country_name`, `revenue_company`, `group_id`.
4.  **Агентный поиск и ранжирование (Python Agent Core):**
    *   Сформировать поисковый вектор на основе профиля клиента + текущей даты.
    *   Выполнить векторный поиск в `news` (оператор `<=>`) с фильтром по `published_at` (последние 30 дней).
    *   Применить rule-based бустинг:
        *   Если `cl_product_loa_mark=true` → повысить вес новостей с темой `cbr_rate`.
        *   Если `fts_flag=true` и `fts_country_name='КИТАЙ'` → повысить вес новостей с темой `ved_china`.
    *   Выбрать топ-N кандидатов.
5.  **Генерация краткого инсайта:**
    *   Для каждой выбранной новости вызвать легкую LLM (Gemma 4 26B или GLM-5.3-Flash).
    *   Передать в промпт: профиль клиента, текст новости, аналитику Альфа-Банка (`is_analytics=true`).
    *   Получить структурированный JSON с полями `summary`, `relevance_score`, `semantic_tags`.
    *   **Самопроверка:** Если LLM не смогла связать новость с профилем клиента — исключить из выдачи или понизить релевантность.
6.  **Формирование ответа:**
    *   Собрать массив инсайтов с пагинацией.
    *   Добавить `semantic_tags` — явное указание, какие признаки клиента повлияли на выбор этой новости (для трассируемости, Критерий №9).
    *   Вернуть HTTP-200.

### 9. Маппинг данных
| Название параметра | В БД | В JSON | Комментарий |
| :--- | :--- | :--- | :--- |
| insight_id | — | UUID | Генерируется агентом при формировании инсайта. Уникален для пары (news_id, synthetic_u). |
| news_id | news.news_id | String | Идентификатор исходной новости/аналитики. |
| title | news.title | String | Заголовок новости. Может быть переформулирован агентом для персонализации. |
| summary | news.summary | String | Краткая выжимка. Если пустая — генерируется агентом. |
| published_at | news.published_at | ISO 8601 | Дата публикации в UTC. |
| source | news.source | String | Название источника. |
| is_analytics | news.is_analytics | Boolean | Флаг аналитики Альфа-Банка. Влияет на отображение бейджа «Мнение банка». |
| relevance_score | — | Float (0-1) | Оценка релевантности, рассчитанная агентом. |
| relevance_level | — | Enum | HIGH / MEDIUM / LOW. Пороги: >0.8=HIGH, >0.5=MEDIUM, иначе LOW. |
| semantic_tags[].tag | clients.* / news.topics | String | Код признака (например, cl_product_loa_mark). |

| sources[].id | news.news_id | String | ID источника, использованного для формирования вывода. |
| sources[].type | news.is_analytics | Enum | alfa_analytics / external_news. |

### 10. Логирование и мониторинг
**Логирование:**
*   **Запрос:** `synthetic_u`, query params, timestamp.
*   **Ответ:** HTTP status, count items, avg relevance_score, processing_time_ms.
*   **Agent Trace:** Для каждого инсайта логировать: выбранные `semantic_tags`, ID найденных новостей, модель LLM, токены (input/output). Это необходимо для Критерия №9 (трассируемость).

**Метрики:**
*   `news_feed_requests_total` — количество запросов к методу.
*   `news_feed_generation_duration_seconds` — время генерации ленты (p50, p95, p99).
*   `llm_tokens_consumed_total` — расход токенов (контроль лимита 500 р).
*   `news_feed_errors_total` — ошибки по типам (4xx, 5xx, LLM timeout).
*   `avg_relevance_score` — средняя релевантность выдаваемых инсайтов (метрика качества персонализации).

**Алерты:**
*   Расход токенов > 80% от дневного лимита → уведомление в канал разработки.
*   p95 latency > 5 сек → алерт (возможно, деградация LLM или БД).
*   Ошибки 5xx > 5 за 5 минут → алерт DevOps.
*   Средняя релевантность < 0.4 за час → алерт продуктовой команде (деградация качества персонализации).

# 3. POST /api/clients/{synthetic_u}/news/{news_id}/chat

**Проект:** Альфа Хак_Новостная аналитика  
**Версия:** 3.0 (Final)  
**Роль Java-компонента:** Оркестратор контекста, Страж бюджета, Трансформатор ответов  

## 1. Логика обработки запроса
Java выполняет следующие действия последовательно при получении запроса от фронтенда:

1.  **Валидация входных параметров.** Проверка формата идентификаторов в URL и содержимого сообщения в теле запроса.
2.  **Проверка лимитов.** Верификация Rate Limit (20 запросов/мин) и прогноза расхода токенов (3000 ток.) до обращения к любым ресурсам.
3.  **Проверка существования сущностей.** Убедиться, что клиент и новость существуют в БД, прежде чем тратить ресурсы на сборку контекста.
4.  **Сборка промпта.** Формирование массива сообщений для LLM путем объединения истории диалога, мета-данных новости и профиля клиента из БД.
5.  **Вызов AI-сервиса.** Передача готового массива сообщений во внутренний сервис Python.
6.  **Обработка ответа.** Обновление счетчика бюджета, генерация ID сообщения и формирование финального JSON для фронтенда.

> **Важно:** Java НЕ передает сырые параметры в Python. Java самостоятельно загружает историю и контекст, формируя полный промпт. Python выступает только как исполнитель LLM-запроса.

## 2. Запросы к базе данных
Для корректной работы метода Java выполняет следующие SQL-запросы к PostgreSQL:

### А. Проверка существования клиента (Gatekeeper)
*   **Цель:** Быстрая валидация перед дорогой операцией сборки контекста.
*   **Запрос:** `SELECT 1 FROM public.clients WHERE synthetic_u = :syntheticU LIMIT 1;`
*   **Результат:** Если запись отсутствует → вернуть HTTP 404 Not Found.

### Б. Проверка существования новости (Gatekeeper)
*   **Цель:** Убедиться, что диалог привязан к существующей новости.
*   **Запрос:** `SELECT 1 FROM public.news WHERE news_id = :newsId LIMIT 1;`
*   **Результат:** Если запись отсутствует → вернуть HTTP 404 Not Found.

### В. Загрузка истории диалога (Context Builder)
*   **Цель:** Получить контекст предыдущих сообщений для формирования промпта.
*   **Запрос:**
    ```sql
    SELECT role, content 
    FROM public.messages 
    WHERE conversation_id = :conversationId 
    ORDER BY created_at ASC 
    LIMIT 10;
    ```
*   **Параметр `conversationId`:** Формируется как конкатенация `{synthetic_u}_{news_id}`.
*   **Результат:** Список пар «роль-сообщение». Если список пуст, этот шаг пропускается.

### Г. Загрузка мета-данных новости (Context Builder)
*   **Цель:** Добавить краткий контекст новости в системный промпт без загрузки полного текста.
*   **Запрос:** `SELECT title, summary FROM public.news WHERE news_id = :newsId;`
*   **Результат:** Заголовок и краткое содержание новости (~300–500 символов). Поле `body_md` НЕ запрашивается.

### Д. Загрузка профиля клиента (Context Builder)
*   **Цель:** Персонализация системной инструкции.
*   **Запрос:**
    ```sql
    SELECT 
        mainokved_name,
        revenue_company,
        COALESCE(cl_product_loa_mark, false) as has_credits,
        COALESCE(fts_flag, false) as has_ved,
        fts_country_name
    FROM public.clients 
    WHERE synthetic_u = :syntheticU;
    ```
*   **Результат:** Набор из 7 семантических полей для обогащения системного промпта.

### Е. Синхронизация бюджета (Фоновый процесс)
*   **Цель:** Корректировка локального счетчика расхода токенов.
*   **Запрос:** `SELECT COALESCE(SUM(tokens_input + tokens_output), 0) FROM public.agent_traces WHERE created_at > NOW() - INTERVAL '24 hours';`
*   **Частота:** При старте приложения и каждые 5 минут. Не выполняется в потоке пользовательского запроса.

## 3. Данные, передаваемые в Python
Java формирует и отправляет во внутренний сервис следующий JSON-объект:

```json
{
  "request_type": "chat",
  "synthetic_u": "U_80",
  "client_profile": { /* 7 семантических полей из запроса Д */ },
  "llm_request": {
    "messages": [
      {
        "role": "system",
        "content": "Ты финансовый советник Альфа-Банка. Новость: '{title}'. Кратко: '{summary}'. Клиент: {industry}, выручка {revenue} руб., кредиты={has_credits}, ВЭД={has_ved}. Отвечай СТРОГО в контексте этой новости и профиля."
      },
      /* Элементы истории из запроса В */
      {
        "role": "user",
        "content": "Текст нового вопроса пользователя из тела HTTP-запроса"
      }
    ],
    "temperature": 0.3,
    "max_tokens": 500
  }
}
```

**Ключевые особенности передачи:**
*   Поле `llm_request.messages` содержит **полностью собранный промпт**. Python не имеет доступа к БД для чтения истории или новости.
*   Системный промпт формируется Java на основе результатов запросов Б, В и Г.
*   История диалога добавляется строго в хронологическом порядке (`ASC`).
*   Новый вопрос пользователя всегда является последним элементом массива.

## 4. Обработка ответа и запись в БД
После получения ответа от Python Java выполняет следующие действия:

1.  **Обновление бюджета.** Добавляет фактическое количество токенов (`tokens_in + tokens_out`) из ответа Python в локальный счетчик.
2.  **Генерация идентификатора.** Создает уникальный UUID для поля `message_id`.
3.  **Формирование ответа.** Собирает финальный JSON со статусом 200 OK, включающий `message_id`, `role`, `content`, `created_at` и `citations`.

**Запись в базу данных:**
*   Java **НЕ записывает** сообщения в таблицу `messages`.
*   Запись вопроса пользователя и ответа ассистента выполняется **асинхронно со стороны Python** после успешной генерации.
*   Java также не пишет трейсы в `agent_traces`; это ответственность Python.

## 5. Проверка корректности архитектуры
*   **Разделение ответственности:** Соблюдено. Java управляет контекстом и бюджетом, Python — генерацией.
*   **Безопасность:** Системный промпт жестко задается Java, исключая возможность инъекций через пользовательский ввод.
*   **Производительность:** Запросы к БД оптимизированы (лимиты, выборка только нужных полей). Пагинация и сортировка истории выполняются на стороне БД.
*   **Надежность:** Асинхронная запись в БД не блокирует ответ пользователю. Бюджетный pre-check предотвращает превышение лимита до вызова LLM.
*   **Соответствие спецификации:** Все требования OpenAPI и Master Document v3.0 учтены. Статус ответа — 200 OK. Структура ответа соответствует стандарту GetAnalyst.

Данная постановка является полной и самодостаточной для реализации метода `/chat` без дополнительных уточнений.

### 8. Требования к реализации (Use Case)
1.  **Валидация входных данных:**
    *   Проверить формат `synthetic_u` и `news_id`.
    *   Проверить наличие записей в `clients` и `news`. Если нет → HTTP-404.
2.  **Получение источников:**
    *   Определить список связанных новостей/аналитики, использованных агентом для данного инсайта.
    *   *Примечание:* Для MVP можно вернуть саму новость + 2-3 наиболее релевантных материала из той же тематики (`topics`). В полной версии — брать из `agent_traces.steps` или отдельной таблицы связей.
    *   Выполнить запрос к `news` WHERE `news_id IN (...)`.
3.  **Формирование ответа:**
    *   Преобразовать записи в массив объектов с полями `id`, `name`, `type`, `title`, `published_at`.
    *   Сортировка: сначала `alfa_analytics`, затем `regulator`, затем `media`. Внутри группы — по `published_at DESC`.
    *   Вернуть HTTP-200 с массивом.

### 9. Маппинг данных
| Параметр JSON | Тип | Поле(я) в БД | Комментарий |
| :--- | :--- | :--- | :--- |
| id | String | news.news_id | Уникальный ID источника. |
| name | String | news.source | Название источника (человекочитаемое). |
| type | Enum | news.is_analytics + logic | alfa_analytics / regulator / media. Определяется по source и is_analytics. |
| title | String | news.title | Заголовок материала. |
| published_at | ISO 8601 | news.published_at | Дата публикации источника. |

### 10. Логирование и мониторинг
**Логирование:**
*   **Запрос:** `synthetic_u`, `news_id`.
*   **Ответ:** HTTP status, count sources, processing_time_ms.

**Метрики:**
*   `sources_requests_total` — количество запросов источников.
*   `avg_sources_per_insight` — среднее количество источников на инсайт (метрика качества трассируемости).
*   `sources_duration_seconds` — время выполнения.

**Алерты:**
*   avg_sources_per_insight < 1 за час → алерт (агент не указывает источники, риск галлюцинаций).
*   p95 latency > 200мс → алерт.
*   Ошибки 5xx > 5 за 5 минут → алерт DevOps.
